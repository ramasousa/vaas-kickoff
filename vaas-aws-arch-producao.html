Network ACLs (camada adicional — stateless)

NACLs como defesa em profundidade sobre os Security Groups. Subnet private-data: bloqueia TODO tráfego de entrada exceto da private-compute. Subnet public: bloqueia portas 22/3389 (SSH/RDP). NACLs são stateless — regras de inbound e outbound precisam ser espelhadas.

Auto Scaling — múltiplas dimensões

scale_out_cooldown      = 60     // segundos — scale-out rápido
scale_in_cooldown       = 300    // segundos — scale-in conservador

# Política 2: Target Tracking — ALB Request Count per Target
requests_per_target     = 200    // cada task aguenta 200 req/min confortavelmente

# Política 3: Scheduled Scaling — pico de IPVA em março/SP
schedule_peak_start   = "cron(0 7 1-31 3 ? *)"   // 7h todo dia de março
desired_during_peak   = 10     // pré-provisiona antes do pico matinal
schedule_peak_end     = "cron(0 22 1-31 3 ? *)"  // 22h — volta ao normal
desired_after_peak    = 3

# Política 4: Step Scaling — spike súbito (sem aviso)
# Se CPU > 85% por 2 minutos consecutivos: +4 tasks (além do target tracking)

Data Layer — Redis Cluster & DynamoDB

Alta volumetria exige Redis Cluster Mode (sharding + replicação) em vez de apenas réplicas. DynamoDB On-Demand absorve qualquer pico sem provisionamento.

ElastiCache Redis — Cluster Mode Enabled

Por que Cluster Mode? Redis com apenas réplicas (Cluster Mode disabled) tem um único primary node como gargalo de escrita. Com 500 TPS e sessões de usuário sendo gravadas a cada requisição, um único primary fica saturado. Cluster Mode distribui os writes em 3 shards — cada shard tem sua própria primary.

Failover VPN — automático via BGP

Failover transparente: quando o Direct Connect cai, o BGP retira as rotas do DX do Transit Gateway e as rotas da VPN (com metric maior) entram automaticamente. A aplicação não sabe que houve failover — apenas a latência sobe de <3ms para 10-15ms. Dentro do SLA de p99 < 4s da jornada completa.

Segurança — Defesa em Profundidade

5 camadas de defesa independentes — falha de uma não compromete as outras.

Camada 1 · WAF v2
Rate limiting: 500 req/min por IP
Geo-blocking: apenas Brasil (CC = BR)
AWS Managed Rules: AWSManagedRulesCommonRuleSet + SQLi
Custom rule: bloqueia enumeração de placas (pattern /^[A-Z]{3}[\d]{4}$/ em volume)
Logging: todos os requests → CloudWatch → Athena
Camada 2 · ALB + ACM
TLS Policy: ELBSecurityPolicy-TLS13-1-2-2021-06
Mínimo: TLS 1.2 (elimina TLS 1.0/1.1 e SSLv3)
Certificado: ACM · renovação automática 60 dias antes
HTTP → HTTPS: redirect obrigatório no listener :80
Security headers: HSTS, X-Frame-Options via Lambda@Edge
Camada 3 · IAM Least Privilege
Task Role ECS: só o necessário:
• secretsmanager:GetSecretValue → 4 secrets específicos
• cloudwatch:PutMetricData → namespace VaaS/*
• xray:PutTraceSegments
• dynamodb:PutItem|GetItem → tabela específica
• kms:Decrypt → CMK específico
Zero wildcards. Zero AdministratorAccess.
Camada 4 · KMS CMK Dedicado
CMK: vaas-tributos-cmk (não compartilhado)
Rotação: automática anual
Key policy: só Task Role ECS + time de segurança
Protege: Redis at-rest, DynamoDB, Secrets Manager, CloudTrail logs, S3
CloudTrail: toda operação KMS auditada
Camada 5 · CloudTrail + VPC Flow Logs
CloudTrail: multi-region, S3 com Object Lock 365 dias (imutável)
VPC Flow Logs: all traffic (ACCEPT + REJECT) → S3 → Athena
CloudTrail Insights: detecta anomalias de API
Config Rules: verifica conformidade contínua (MFA, public S3, SG rules)
BACEN 4.658: todos os itens Art. 5º atendidos
Secrets Manager · Rotação
Secrets: axway-client-id, axway-client-secret, redis-auth-token, ciam-jwks-url
Rotação: Lambda automática a cada 30 dias
Zero downtime: Lambda atualiza o secret e notifica ECS para recarregar
KMS: cada secret cifrado com CMK dedicado
Audit: todo acesso logado no CloudTrail

Step-Up Authentication — pagamentos

Obrigatório antes de produção: toda chamada a /debito/pagamento requer confirmação biométrica no app Bradesco via push notification (FCM/APNs). O MCP Server não executa o POST no Axway sem receber o callback de confirmação. Ladrão com celular furtado não passa pela biometria do titular. Spec detalhada no documento de Segurança de Sessão.

X-Ray — Trace distribuído

Trace end-to-end: cada requisição do app Bradesco gera um trace ID que percorre: ALB → ECS (MCP Server) → Bedrock (KB lookup) → DynamoDB (idempotência) → Axway (via VPN). No X-Ray Service Map, é possível ver exatamente onde está a latência em qualquer step da jornada. O correlationId (sagaId) é injetado no trace para cruzar com os logs do Axway.
